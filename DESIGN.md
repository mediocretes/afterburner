# How afterburner works

This is the design document: enough to pick the project up cold. The README covers using it.

Status: 0.1.0, a working prototype. Verified end to end against the live web game (v3.0.1) in a headless
browser (`rake e2e`, 15 checks), and by hand in the Steam build on macOS and Windows. Unit tests pass on
Linux, macOS, and Windows.

## The shape of it

Bitburner runs only JavaScript, inside the game. A Ruby script therefore runs *outside* the game, in an MRI
process on your machine, and borrows the game's `ns` over a WebSocket:

```
 src/scout.rb                                          the game (browser or Steam)
     │                                                ┌──────────────────────────────┐
     │  afterburner watch (one process, one port)     │ Remote API client ──────┐    │
     ├─ Stubs: scout.rb → scout.js (RAM claim) ──push─┼─▶ home: scout.js        │    │
     ├─ FileSync: dist/** ───────────────────────push─┼─▶ home: other files     │    │
     │                                                │                         │    │
     │  ws /        ◀── GameLink (JSON-RPC) ──────────┼─────────────────────────┘    │
     │  ws /script  ◀── Session ◀──── WebSocket ──────┼── run scout.js (the stub)    │
     │                  runs scout.rb; each ns call   │      serve(ns, "scout.rb")   │
     │                  goes back to the stub ───────▶│      makes the call          │
     │  ws /console ◀── afterburner console (IRB)     └──────────────────────────────┘
     │  GET /save, /ram, /sources ◀── afterburner save / ram / restore
```

- **The stub** (pushed as `scout.js`) is a few lines: `ns.ramOverride(<cost>)` as the first statement of
  `main`, then `await serve(ns, "scout.rb", 12525)`. The override claims the script's RAM up front; it is also
  what makes the game skip its own static scan of the stub (whose real calls are dynamic, `ns[name](...)`).
- **The proxy** (`lib/afterburner/proxy.js`, pushed as `afterburner/proxy.js`) holds `serve()`. It connects to
  `ws://localhost:<port>/script`, sends `start`, then loops: make the call it's asked to, send back the result.
  It closes the socket in `atExit`, so killing the stub stops the Ruby script. If afterburner isn't there, it
  retries every 2 s for a minute before failing: a save that loads restarts its scripts at once, possibly
  before afterburner is up. On the server side, a script that arrives before the game has sent its
  definitions waits up to 30 s for them.
- **Session** (`session.rb`) runs one script. One Async task runs the script; another reads the socket. A
  closed socket cancels the script task wherever it is (inside an `ns` call, or in Ruby's own `sleep`), and its
  `at_exit` blocks run.
- **GameLink** (`game_link.rb`) is the game's Remote API connection. The game is the WebSocket *client*;
  afterburner sends it JSON-RPC requests. One link at a time; a new connection replaces the old.
- **Stubs** (`stubs.rb`) are built in memory and pushed straight to the game, never written to disk. Rebuilt
  when a script, the definitions, or the measured costs change; only changed stubs are pushed. A stub whose
  script is gone is deleted from the game, including ones left from an earlier run (found on connect by their
  `// Generated by afterburner` first line).
- **FileSync** (`file_sync.rb`) does bitburner-filesync's job for everything else: push all on connect, then
  changes; deletions if `allowDeletingFiles`. Polls every 0.5 s rather than using OS file events.
- **Server** (`server.rb`) ties it together on one port, routing by path, and runs the 0.5 s tick that drives
  FileSync and Stubs.

### When the game connects

1. `getDefinitionFile` → saved as `NetscriptDefinitions.d.ts` (the RAM scan and the `ns` names come from it).
2. Every synced file is pushed.
3. The proxy and every stub are pushed; `getAllFiles` finds stale stubs to delete.
4. Copies of the proxy that scripts put on other servers are brought up to date: `getAllServers` for the
   servers you have root on, `getFileNames` for which have `afterburner/proxy.js`, `getFile` to skip ones
   already current. A failure here (an older game without `getAllServers`, say) is logged and nothing else.

## Protocols

**Remote API** (the game's; afterburner is the server, the game the client): JSON-RPC 2.0. afterburner uses
`pushFile` (to home, and to other servers for proxy copies), `deleteFile`, `getAllFiles`, `getDefinitionFile`,
`getSaveFile`, `calculateRam`, `getAllServers` (which lists every server, found or not), `getFileNames`, and
`getFile`. The game also offers `getFileMetadata` and `getAllFileMetadata`. There is no way to run a script; that's what stubs are for. Handlers:
bitburner-src `src/RemoteFileAPI/MessageHandlers.ts`.

**Scripts** (afterburner's own, on `/script`), JSON text frames, one socket per running script:

```
stub → afterburner  {op: "start", script: "scout.rb", args: [...], pid: 3, ram: 2.25, resumed: false}
afterburner → stub  {op: "costs", names: [...]}         (at most once a minute; see RAM)
stub → afterburner  {op: "costs", costs: {"hack": 0.1, ...}}
afterburner → stub  {op: "call", id: 1, path: ["hacknet", "numNodes"], args: [...]}
stub → afterburner  {op: "result", id: 1, value: ...} | {op: "error", id: 1, message: "..."}
afterburner → stub  {op: "exit", message?: "..."} | {op: "fail", message: "..."}
```

`ram` is what the stub claimed, for hot reload. A script makes one call at a time, so the game never sees
concurrent `ns` calls from it. A `path` naming a
non-function (`["enums"]`) reads the property. JSON can't carry `Infinity` or `NaN`, so both sides tag them as
`{"$num": "Infinity"}`. `fail` makes the stub throw, so the game shows its usual error dialog, with the Ruby
message and backtrace. An `exit` message goes to the script's log, with no dialog.

When afterburner goes away mid-run (restarted, or stopped), a stub doesn't end: it logs that to its own log and
reconnects, every 2 s for a minute and then every 10 s, with no deadline. When it's back, the stub sends `start`
again with `resumed: true`, and afterburner runs the script from the top in the same process. A kill in the game
still ends it (the stub's `atExit` sets a flag first), and so does the console stub, whose IRB went with
afterburner. On a resume afterburner checks the code against the claim, since the code may have grown while it
was away: if it no longer fits, it sends `exit` with a message saying to run it again, rather than letting the
game kill it at the first call over. Resumes are logged at debug; the server sums them up in one line once
they've stopped arriving for 3 s.

**Console** (`/console`): `afterburner console` connects with `?ram=`, GB or a percentage (default `80%`).
afterburner pushes `afterburner/console.js`, a stub with that claim whose script is the special name `@console`,
and sends `status` messages until it's run. A percentage is worked out by the stub, since only the game knows
the server it runs on. It starts at 1.7 GB (base plus `getServerMaxRam` and `getServerUsedRam`), then claims
the share of what's free plus what it holds. The stub's `start` carries what it holds, and the console reports
that.

Every stub's `main` starts with `ns.ramOverride(<number>);`. The game reads that as the script's whole static
RAM without scanning the code, but only as the first statement and only with a literal. Anything else and it
charges every name in the stub and `proxy.js` that matches any `ns` function, which for the console stub came
to 33.7 GB. Then it relays: `call` frames from the console to the stub, `result`/`error`
back. Leaving the console sends the stub `exit`; the stub stopping sends the console `ended`. On the console
side, IRB runs on the main thread and the WebSocket in a background thread's reactor, talking through queues.

**`/save`, `/ram?file=`, and `/sources`**: plain HTTP for the CLI. `/sources` lists the save's copies of the Ruby scripts, with contents and `mtime`, for `afterburner restore`. `/save` returns the bytes `getSaveFile` describes (a
binary save arrives as one character per byte) with a suggested file name; `/ram` returns `calculateRam`.

## The Ruby side

One resolver (`Api#resolve`, built from the definitions file) decides what a name means. The `ns` proxy and
the RAM scanner both use it, so anything a script can call is something it's charged for.

- snake_case, with the JavaScript name accepted too.
- `get_` dropped when that collides with nothing: `ns.server_max_money`, `ns.player`.
- `?` for questions: functions returning a boolean and named `is…`, `has…`, `can…`, `in…`, `get…`, or
  ending in `Exists`/`Running`/`Enabled`. Not for functions that act and report success (`nuke`, `scp`, `kill`).
  `has_` is dropped too: `ns.root_access?`.
- A short name never shadows a real function.
- Keyword arguments become the trailing options object, keys camelCased.
- `NS` is a `BasicObject`, so names like `print`, `format`, and `sleep` reach the game rather than `Kernel`.
  Besides the game's names it answers only Ruby's reflection protocol (`inspect`, `respond_to?`, and `methods`,
  which lists the Ruby names so IRB can tab-complete them). IRB only completes after a variable or a constant,
  so the console prompt also has `ns` as a local.
- `AB` holds afterburner's own tools (`AB.functions`, `AB.doc`), so they never collide with a game function. It
  finds the API through the same fiber-local session as `ns`. Docs come from the definitions file: the parser
  keeps each member's JSDoc and signature, and `AB::Docs` renders them with Ruby names. An options object as the
  last parameter shows as `**opts` with its fields listed as keywords.
- `Record` wraps game objects: snake_case readers, `?` predicates (dropping `has`/`is`), `[]`, `keys`, `to_h`,
  pattern matching. `methods` adds the readers (and predicates for yes/no fields) so IRB completes them. Sent
  back to the game as the original object.
- Each run is `load(path, fresh_module)`, so scripts' constants and methods don't leak into each other. The
  module provides `ARGV`, `NetscriptError`, and per-script `at_exit`, `abort`, `exit`.
- `ns` and `logger` are private `Kernel` methods (`ScriptAccess`) that look up the running script's session in
  fiber-local storage, as `$stdout` routing does, so they work anywhere in a script's code: libraries, its
  classes, methods added to `Numeric`. Async tasks a script starts inherit the storage; a `Thread` doesn't, and
  outside a script they raise a `NameError` saying so. The console sets the same storage, so `ns` works inside
  classes defined at its prompt. The RAM scan already charges a bare `ns` in any file it reaches. It
  also holds every top-level class and module (Ruby's, and libraries'): a class definition looks only in the
  module it's in, so without them `class Float` in a script would make a new `Float` in the script's module
  and a monkeypatch would silently do nothing. A class a script defines itself stays in its module. The module
  is built before the script runs, so a library the script loads can define classes it doesn't have yet; the
  module's own `require`, `require_relative` (resolved against the caller's file, as Ruby's is), and `load`
  share any new top-level classes into it afterwards, never replacing a name the script defined itself.
  Otherwise `class Server` after `require_relative 'lib/server'` made an empty `Server` the first time the
  library loaded in afterburner's process, and reopened the real one after that. The console prompt is built
  the same way, so the same holds there. That `load` sends a `.rb` file through `require` (forgotten first, so
  it runs again), for the reason library reloads do: a plain `load` evaluates under the thread's top-level
  wrapper, which is another script's module while that script is paused inside its own wrapped load.
- The console's prompt is a script's top level. `Console#prompt_binding` loads `console_prompt.rb` wrapped in a
  fresh `ScriptContext` module, as a script is loaded, and IRB runs on the binding that file leaves behind. So
  what works at the prompt works in a script: the same constants (afterburner's own `Server` and `Record` are
  out of sight), `ARGV`, top-level methods kept in the module, and `class Float` reopening the real one. Only
  `ns` differs, as a local rather than a method, for tab completion; it's the same object.
  `require_relative` resolves against the scripts folder, as for a script at its top (Ruby's own would look
  beside `console_prompt.rb`, in afterburner).
- `$stdout`/`$stderr` are replaced (in `watch`) by an object that routes writes by fiber-local storage: inside a
  script they go to its terminal (`ns.tprint`), elsewhere to the real stream. So `puts` works from classes and
  gems too. `logger` writes to `ns.print`.
- `at_exit` blocks run before the game hears a script is done, so they can still use `ns`. After a kill they
  run too, but `ns` calls in them raise rather than wait for an answer that won't come.

## Ruby sources in the save

`SourceBackup` keeps a copy of every `src/**/*.rb` in the save as `afterburner/src/<name>.txt` (the game stores
only script and `.txt`/`.json`/`.css` files), so the code travels with it. On connect it pushes each script
unless the save's copy is identical, or newer by the game's `mtime` (from `getAllFileMetadata`, allowing 2 s of
clock difference); a newer copy is left in place with a warning. Copies with no local file are reported, not
deleted: they may be another machine's. While connected, edits are pushed and deletions remove the copies
this session put there.

`afterburner restore` (`SourceRestore`, via the server's `/sources`) is the only way code comes back out, on
purpose: any in-game script can write files to the save, so automatic restoring would let one plant Ruby that
afterburner runs on the host. It writes missing files and newer copies, keeps newer local files unless
`--force` (backing them up to `.afterburner/replaced/<time>/`), and refuses names that would land outside
`src/`.

## Hot reload

The server's tick compares the mtimes of every `.rb` under `src/`. When a file changes, each running Session
whose files (its script plus whatever it `require_relative`s, from the RAM scan) include it is asked to reload:

1. Changed libraries that are loaded are required again first, whether or not anything is running, so the
   next run gets the new code (restarting running scripts is what `--no-reload` turns off) (deleted from `$LOADED_FEATURES`, then
   `require`d). Not `load`: a plain `load` evaluates under the thread's current top-level wrapper, and that
   state is per thread, not per fiber, so while any script sits paused inside its own wrapped `load`, a
   library re-`load`ed from the server lands inside that script's anonymous module. `require` always
   evaluates at the real top level. Its constants get redefined, and so do a monkeypatch's on every run, so
   `RedefinitionWarnings` (a `Warning.warn` filter) drops Ruby's "already initialized constant" and "previous
   definition of" warnings for files under the scripts folder; they would only land in a script's terminal. A
   failed reload leaves the library out of `$LOADED_FEATURES`, so the next run's `require_relative` loads it,
   which is when they used to show.
2. `Session#reload` rescans the script and checks the RAM. The game charges each distinct function once per
   process, so what the new code needs is the base cost plus everything the session has called so far plus
   everything the new code calls. If that exceeds the stub's claim (`ram` from `start`), the old code keeps
   running and the log says to run it again (the stub itself has already been re-pushed with the new figure).
3. Otherwise the script's task is stopped and a new run starts in the same session: same stub, pid, socket,
   and arguments, a fresh module. It first runs the old code's `at_exit` blocks (`ns` still works), then
   prints `afterburner: reloaded` to the script's log.

A call the old code had in flight still completes in the game (the stub handles one message at a time); its
late answer is recognised by its id and dropped. A reload can only start while the script is running, and a
run restarts only if a reload actually stopped it, so a script that has just finished isn't brought back.

## RAM

The game charges 1.6 GB per script plus each distinct function the code mentions, and kills a script at the
exact call that exceeds its claim (verified). So a stub's claim must be exact: too low gets the script
killed, too high wastes RAM.

**Scan** (`ram_scanner.rb`, Prism): charges calls whose receiver chain starts at `ns`, `@ns`, a local or method
named `ns`, or a variable assigned a namespace or `ns` itself; plus `ns.public_send(:name, ...)` (or `send`,
`__send__`) with a literal. `NS` defines `public_send` and `send` itself, since `BasicObject` has only `__send__`.
Follows `require_relative`.

Only reachable code is charged. The scan splits the code into units: each file's load-time code (everything
outside a `def`), each method by name (`def`, `def self.x`, `define_method(:x) { }`), and the lambdas a constant
holds as plain data, by the constant's name. Plain data means the constant's value itself, or inside arrays and
hashes of it, perhaps `.freeze`d: an `OPENERS` table of `->(host) { ns.brutessh(host) }` runs only when something
uses `OPENERS`. A lambda that's called or passed somewhere while the value is built (`-> { }.call`,
`Command.new(-> { })`) runs then, so it stays with the load-time code; `A = B = -> { }` reaches B's lambdas from A.
Load-time code is reachable from the start. A reachable unit reaches every method whose name it calls, in any
class (name-based, so it over-charges a little and never misses a method), and the lambdas of every constant it
reads, including `const_get` with a literal (each part of `"A::B"`). Names count as called when called; when they
are the reader and setter behind an attribute write (`obj.x += 1`, `obj.x ||= v`, `obj.x, y = ...`) or `[]`/`[]=`
behind an index write; when passed as a literal symbol or string (`send(:x)`, `map(&:x)`, `inject(:+)`,
`method(:x)`; not declarations like `attr_reader :x` or `define_method(:x)`); when aliased; as compound operators
(`+=`); as backticks; and when Ruby, the standard library, or afterburner itself calls them (`RamScanner::IMPLICIT`:
`initialize`, conversions, `each`, comparisons, `hash`, `coerce`, `call`, exception `message`, `Hash#default`,
`write` for IO-like objects, `method_missing`, the hooks, and so on).

If reachable code dispatches in a way the scan can't follow, it charges every unit and says why: `public_send`,
`send`, `method`, `singleton_method`, `to_enum` with a name it can't read (on anything but `ns`), or with a name
that dispatches again (`send(:public_send, ...)`, `method(:eval)`); `eval`/`class_eval` of a string; `const_get`
or `alias_method` with a name it can't read; block-less `inject` with an operator it can't read; a block argument
(`&x`) that isn't a literal symbol, a lambda or proc, `method(:x)`, a variable holding a lambda, or the method's
own `&block`; and `to_proc` on something else. `afterburner ram` prints the reason and the watch logs it once.
`afterburner ram` also lists the charges it skipped as unreachable. The rules came out of an adversarial review
that ran every candidate miss for real; anything new of that kind should get a test in `ram_scanner_test.rb`.

Known gaps, older than the reachability rules: `ns` reached in ways the alias tracking doesn't see (`GAME = ns`,
`@x ||= ns.hacknet`, `self.ns`, `send(:ns)`, Forwardable delegation to `@ns`), and code loaded by anything but
`require_relative` with a literal path (`require File.expand_path(...)`, `load`, `autoload`, globbed requires),
which the scan never reads. Calls on results (`ns.server(t).money_max`) aren't charged. Names that don't
resolve are logged ("ns.hakc isn't a Netscript function"). A call the scan can't see gets the script killed by
the game, and the proxy appends a hint.

**Costs**: the documented `RAM cost:` lines are right for nearly every function, but some functions' costs
depend on the player's progress (66 of 526 differed in a fresh game, all in parts of the game you reach later).
So when a script starts, at most once a minute, its session asks the stub to measure every cost with
`ns.getFunctionRamCost` (free), and caches the answers in `.afterburner/ram-costs.json`. Stubs prefer measured
costs and are re-pushed when they change. The very first stubs use the documented numbers.

The end-to-end test compares a stub's claim with the game's own `calculateRam`, and checks the measured table
against the game for every function.

## Security

Granting the game local network access lets any script in the game reach localhost, and afterburner runs Ruby:

- It listens on localhost only.
- Browser WebSockets on `/` and `/script` must come from the game: the web build's origin, `file://` (Steam,
  which loads the game from a file), or `http(s)://localhost:*` (a locally
  served build, e.g. a fork). A missing `Origin` (a local non-browser client) is allowed: local processes can
  already run anything.
- `/console`, `/save`, and `/ram` refuse anything with an `Origin`, i.e. any browser.
- Only `.rb` files under `src/`, by plain relative name: no `..`, no absolute paths, nothing under `lib/`. The
  game never sends code.

What it can't prevent: anything in the game can start any script in `src/`, with arguments of its choosing.
A stub is an ordinary file in the save, so in-game code can write its own or copy one, and a secret embedded
in stubs would be just as readable. That can't introduce code, since only what's already in `src/` runs, but
a script that acts on the host (files, the network, shelling out) should treat `ARGV` as untrusted input.
Scripts that only call `ns` give the game nothing it couldn't already do.

It is not a sandbox for the Ruby you write.

## Platforms

- **Web build in Chrome**: verified. Chrome's Local Network Access blocks `ws://localhost` from the https game
  page until the user grants the site permission (Playwright: `permissions: ["local-network-access"]`).
- **Steam build**: loads the game with `window.loadFile("index.html")`, and its WebSockets carry
  `Origin: file://` (seen on macOS). It sets no permission handler, so Electron grants local network access
  without asking. It also disables background throttling: scripts keep full speed when the window isn't
  focused, unlike a background Chrome tab. Tested by hand on macOS and Windows.
- **Windows**: tested by hand with the Steam build (Ruby 4.0.7 from RubyInstaller with DevKit), and the
  unit tests run there in CI. `io-event` uses its pure-Ruby `select` backend there. In PowerShell, run
  `ridk.cmd` rather than `ridk`: the default execution policy blocks `ridk.ps1`.

## Known limits

- Scripts are fibers on one thread: Ruby that never yields (no `ns` call, `sleep`, or IO) blocks every script,
  and a kill can't interrupt it.
- `ps` shows `scout.js`, not `scout.rb`.
- Port handles and React-node printers don't cross.
- Reloading the game drops every script's socket.
- One socket per running script.

## Keeping it working

What's most likely to break, and what watches for it:

- **The definitions format.** The parser reads `NetscriptDefinitions.d.ts` line by line, relying on its
  generated formatting. The `Upstream definitions` workflow parses the game's current `stable` and `dev`
  copies weekly, and `afterburner watch` warns if a connected game's file yields suspiciously few functions.
- **The game's UI**, for the end-to-end test only: it clicks "Exit Tutorial", "Options", "Remote API", the
  second text field (the port), and "Connect".
- **async's internals.** Stopping a task raises `Async::Cancel` in async 2.46 (`Async::Stop` before); the
  code rescues whichever of those exist (`Afterburner::STOPPED`). The server binds its port up front, so a
  busy port is an error message rather than a quiet failure in a background task.
- **The game's error text.** `NetscriptError.from_game` strips the "RUNTIME ERROR … (PID - n)" header, and
  the proxy's RAM hint looks for "RAM USAGE ERROR"; if either wording changes, you just get the raw message.
- **The game's origin.** The web build's is fixed; Steam's is `file://` (seen on macOS). If either
  changes, `--origin` accepts the new one without a code change, and `--verbose` logs every connection's
  origin.

- **The locale.** Started without `LANG` (from a launcher, a scheduler, an editor), Ruby takes files to be
  US-ASCII, and the game's definitions file isn't ASCII. afterburner reads every text file as UTF-8
  (`Afterburner.read_text`), and the CLI sets `Encoding.default_external` to UTF-8 so scripts behave as they do
  in a terminal.

`--verbose` logs every message between afterburner and running scripts.

## Next steps

- **A fork of the game** (bitburner-src), if `.rb` should be first-class: teach the module loader to accept
  `.rb` and synthesise the stub, so `ps`/`run` show `.rb` and no stubs exist. RAM could come from afterburner at
  load time. Costs: permanent rebasing, and saves holding `.rb` files won't load in the stock game. Touch
  points: `src/utils/ScriptTransformer.ts`, `src/Script/RamCalculations.ts`, `src/Paths/ScriptFilePath.ts`,
  `src/RemoteFileAPI/MessageHandlers.ts`.
- **Two-way sync**, using `getAllFiles` and file metadata, for scripts edited in the in-game editor.
- **Multiplexing** scripts over one socket, if Ruby scripts ever run in the hundreds.
- **`autocomplete`** in stubs, for tab completion.
- A Ruby-shaped object layer over `ns` (`ns.servers["n00dles"].hack`) is deliberately left to users: it encodes
  gameplay choices.
